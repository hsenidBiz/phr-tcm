The ideal tech stack for what this app has become — a Windows desktop companion for Azure DevOps (bulk test-case authoring, a test runner, and a work-item board) — optimised for the two things that matter: a fast, easy-to-evolve data layer and a modern, endlessly customizable UI.

First, honesty: what "fastest backend" means here

This app has no compute-bound backend. Every candidate language chews through its data in milliseconds.

The data is small…

  • ≤ a few hundred test cases per PBI
  • ≤ 500 board work items (WIQL-capped)
  • Dozens–hundreds of plans/suites; xlsx files of a few thousand rows
  • Local compute is trivial except xlsx parsing, XML building, image capture

…so the bottleneck is the network

  • Azure DevOps REST latency dominates every interaction
  • Writes are budgeted at ~2/sec with Retry-After on 429
  • Reads batch at 200 ids per call
  • Perceived speed = parallel orchestration + caching + optimistic UI
The reframe: "fastest" is delivered by cold start, footprint, concurrent request orchestration, cache architecture and optimistic updates — not raw CPU. The recommended stack wins precisely that definition: a ~10 MB compiled core that launches in under a second, runs requests concurrently on tokio, and makes optimistic UI the default idiom rather than a hand-built pattern.

Criterion 1 — fast backend, easy improvements

The load-bearing decision: where Rust ends and TypeScript begins

Not "Rust for hot paths" — hot paths barely exist here. The boundary that makes this stack work is:

Rust owns everything that touches I/O, secrets, wire formats, or invariants. TypeScript owns everything that touches the user.

In Rust (stable, written once)

  • ADO client with the same typed error taxonomy as today (401 / 403 / 404 / 429 / other)
  • Token-bucket write limiter · retry / Retry-After handling
  • PKCE auth; token in Rust memory only
  • Steps-XML and xlsx round-trip · screenshot capture · settings

In TypeScript (changes weekly)

  • Every screen, form, dialog, and board rule
  • Queue & review UX, duplicate-warning presentation, theming
  • Column/category mapping, validation messages
  • All the things that actually ship multiple times a week

Why improvements stay easy

  • The Rust surface is exactly the part of today's app that is already stable, documented and unit-tested (the Qt-free modules are the only tested code in the current repo). It gets built once against ported golden tests, then ossifies — so Rust compile times never tax the weekly cadence.
  • The churn layer has sub-second feedback. Vite HMR beats any PyQt restart loop, and React/TS is the single strongest ecosystem for AI-assisted iteration — which is how this app is actually developed.
  • Invariants become structural instead of conventional. Today "no DELETE calls" is a docstring promise; in the rebuild the HTTP wrapper exposes no delete method and CI greps the core crate for Method::DELETE. Today the token sits in Python memory shared with all GUI code; in the rebuild no IPC command returns it — a buggy or compromised frontend dependency cannot exfiltrate what it can never see.

Criterion 2 — customizable, modern, sleek, fast frontend

The styling ceiling disappears

The current app repeatedly hit PyQt's limits: stylesheets on item views silently break row painting (forcing custom delegates), the calendar had to be hand-painted to look modern, and the window chrome is a custom frameless implementation fought into shape against Win11. With Tailwind + vendored shadcn/ui, components are files in your repo built on Radix primitives — restyling a calendar or a kanban card is minutes of CSS-token work, not an afternoon of QPainter. The existing light/dark token dictionary maps one-to-one onto CSS custom properties; dark mode becomes a class toggle instead of a refresh_theme() cascade through every screen.

The threading and caching pain is solved by the platform

Today every network call needs a hand-rolled worker plus _loaded/_loading flag pairs, and three ad-hoc caches with manual invalidation. TanStack Query replaces all of it with declarative staleness, retries and background refetch — and the app's signature optimistic-update pattern (merge the PATCH response locally, never refetch) is literally the library's built-in setQueryData idiom: five lines instead of a bespoke worker.

Performance headroom

  • TanStack Virtual renders 10,000-row lists at 60 fps — the 500-item board is trivial.
  • dnd-kit gives pointer-accurate kanban drag-drop with animation, replacing custom QListWidget drop handling.
  • WebView2 is hardware-accelerated and already resident on Win11 — nothing to bundle.
  • The compact always-on-top runner stays a first-class citizen: multi-window is core Tauri 2 API.

Alternatives considered — and where each would win

StackGenuine strengthsWhy it loses here
Electron + React
closest runner-up		 Identical frontend win; Node core is simpler than Rust; fully sufficient for a network-bound workload. Reproduces the exact stated pain in a new costume: 80–150 MB installer, 150–300 MB RAM, slower cold start, and you ship (and patch) your own Chromium. Token isolation is weaker than a Rust core. Would win if Rust were refused outright.
.NET 8 + WinUI 3
rejected		 Best-in-class MSAL.NET; native performance; first-party Microsoft alignment with ADO. Fails the iteration criterion: restyling XAML means control templates and visual states — an order of magnitude more ceremony than Tailwind — and AI assistance for WinUI is markedly weaker. The MSAL edge is muted anyway: the org's accepted flow is browser + loopback, which Rust does identically. Would win if a C# team inherited the tool.
Flutter desktop
rejected		 Excellent rendering performance; pixel-perfect custom UI is its whole thesis. Windows desktop is a second-tier target, with ecosystem gaps exactly where this app lives: virtualized data grids, markdown editing, MSAL. Everything is custom-drawn, so "sleek" costs more, not less.
Python + PySide6/QML
rejected		 Biggest port savings by far — the ADO client, parsers and auth carry over nearly untouched. Keeps the platform tax: still a ~300 MB frozen dist, slow cold start, poor GUI testability, and QML has its own styling ceilings. Every screen still needs rewriting — most of the cost, little of the reward.
Local FastAPI + webview
rejected		 Keeps Python domain code and gets a web frontend. Strictly dominated by Tauri: the same architecture plus an HTTP server to manage, a localhost attack surface for the token, two processes to package — and the PyInstaller freeze problem returns.

Top 5 risks — and their mitigations

RiskMitigation
Rust learning curve / compile times throttle the multiple-releases-per-week cadence. The boundary design is the mitigation: ~10–15 Rust commands, written once against ported golden tests, then rarely touched — day-to-day iteration is Vite HMR. Escape hatch: the React UI and IPC contract survive a core swap to Electron/Node; the UI investment is never hostage to Rust.
WebView2 quirks on the corporate Win11 image (sleep/resume renderer crashes, GPU flashes, group-policy version pinning). Phase-0 spike on the actual corp machine before committing; set window background color, disable ctrl-wheel zoom, add crash-detect-and-relaunch. Evergreen runtime is serviced by Windows Update.
Frameless chrome regressions — snap layouts, rounded corners, drag regions (the same fight the Qt app had). Phase-0 spike with tauri-plugin-decorum; pre-approved fallback is a native frame with overlay titlebar styling. Chrome polish is explicitly not allowed to block Phase 1.
Auth edge cases — loopback port blocked, non-default browsers, refresh expiry or Conditional Access challenges mid-batch. Port the exact proven semantics: same client id, configurable loopback port range, silent refresh in the header getter, hard 401 → pause queue → interactive re-sign-in → resume the in-flight item without re-creating it. Add CAE claims-challenge passthrough (which the Python app lacks).
The SQLite cache becomes a correctness liability if built too early (stale merges, watermark drift, migrations). Deferred by design to the Work Manager phase, where instant board cold-start is its payoff. Read-through only, server always wins, one-keystroke cache nuke. Never a source of truth.

Migration path — from PyQt5 to the new stack

Ports as spec, not code

  • app/api/devops_client.py — the full ADO REST contract: endpoints, error taxonomy, 200-id batching, PATCH add-op, blank-never-wipes rules
  • app/utils/import_parser.py + its tests — the 9-column xlsx round-trip becomes Rust golden vectors
  • app/utils/xml_builder.py + its tests — steps-XML rules (ids start at 2…)
  • app/auth/msal_auth.py — the exact auth flow semantics
  • app/gui/mywork_screen.py — the Work Manager behaviour spec

Rewritten · unchanged

  • Rewritten: all of app/gui/ (~500 KB of PyQt5 — by design), the threading model (deleted → TanStack Query), the theming machinery (tokens survive as CSS variables)
  • Identical: the two-repo release model, the no-DELETE invariant, the in-memory-token invariant, and the xlsx format — users' existing sheets work on day one
  • Coexistence: new app gets its own settings dir + its own Velopack app-id/feed; one-time read-only import of the old settings; both apps run side-by-side until parity

Six phases — the release pipeline ships in Phase 0, not at the end: the weekly-shipping muscle must work from week one.
