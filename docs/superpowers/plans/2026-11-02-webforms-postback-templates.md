# API templates: WebForms postback steps - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A template step can be a full WebForms postback (`postback: { page, button, argument?, fresh? }`): TCM carries the page state in the page itself, chains it across steps of one run, checks and captures from the HTML answer, and every existing template path (prove, run, fixtures, flows, one-off `send_api_request`, guide, UI) takes it.

**Architecture:** The format gains `Step::postback` and `Expect::html` (`api_templates/mod.rs`), checked by `check`. A new module `api_templates/postback.rs` holds the wire contract with the page: `POSTBACK_FN` (in-page JS beside `FETCH_FN`: DOMParser, a per-run `window` map of page key -> last answer HTML, building and sending the post, `html` checks, `html:` captures, `(page state)` scrubbing), the Rust request it is given, the reply it hands back, and the pure judging of that reply. `runner.rs` routes a postback step to it, keeps per-run "which pages are carried" (names only), and never retries a postback. HTML and page state never reach Rust; only field NAMES, check results, capture values and an already-scrubbed excerpt do.

**Tech Stack:** Rust (Tauri 2, serde, specta/tauri-specta, CDP `Driver`), in-page JavaScript run through `Runtime.callFunctionOn`, React 19 + TypeScript, vitest.

**Spec:** `docs/superpowers/specs/2026-11-02-webforms-postback-templates-design.md` (owner-approved). Its "Settled after the builder check" section is binding and overrides anything looser earlier in the spec. Executors read both documents.

## Rulings on spec ambiguity (binding for the tasks)

1. **Format.** A postback step leaves out `method`, `path`, `query`, `json`. So `Step::method` becomes `Option<Method>` (`skip_serializing_if = "Option::is_none"`) and `Step::path` becomes `#[serde(default, skip_serializing_if = "String::is_empty")]`; code reads the method through `Step::method()` (Post for a postback). A non-postback step with no method is refused by `check`.
2. **Where `html` lives.** `expect.html` and `html:` captures are allowed ONLY on postback steps; a postback step refuses `expect.json` and `$` captures (its answer is HTML). `rows` is the single object the spec shows.
3. **Button.** The control is found by `name` equal to `button` or ending in `$<button>`, or - for a LinkButton/grid command that has no name - by a `__doPostBack('<target>'` in an `href`/`onclick` whose target equals `button` or ends in `$<button>`. A submit `<input type=submit|image>` / `<button type=submit>` posts `name=value` with an empty `__EVENTTARGET`; anything else posts its FULL name/target as `__EVENTTARGET` and `argument` as `__EVENTARGUMENT`. Zero matches or more than one: the step fails before sending.
4. **What a browser would send.** Disabled controls are not sent; unchecked checkboxes/radios are not sent; a template value `""` for a checkbox/radio unchecks it (omits it); a `select multiple` sends each selected option; a template field the page does not have is still sent and named in the step detail (`not on the page: a, b`). A template `form` key starting `__` is refused by `check`.
5. **Signed out.** The answer (or the first GET) is the sign-in page when it has an `input[type=password]` and the page posted from had none. That is the existing "signed out" failure (`session_ended`).
6. **Visible.** For `shows`/`hides` text and selector matches, an element is hidden when it or an ancestor has the `hidden` attribute, an inline `display:none` or `visibility:hidden`, or is `input[type=hidden]`, `script`, `style`, `noscript` or `template` (DOMParser applies no stylesheet - ASP.NET validators render inline `display:none`).
7. **No token for postbacks.** A postback does not send the `RequestVerificationToken` header. A template or one-off whose steps are all postbacks (or GETs) runs when its token page has no token.
8. **One-off postbacks are never saved as templates** (one that carried on cannot stand alone); the answer says so with `POSTBACK_NOT_SAVED`.
9. **An empty 400 on a postback is not retried** either (rule 5 of the settled section: never retried automatically).

## Review Focus

1. A LinkButton or grid command with no `name` attribute, only `javascript:__doPostBack('ctl00$Main$lnkCreate','')`: the template's `"button": "lnkCreate"` must find it and post the full target (Task 3 live test `a_link_button_posts_its_dopostback_target`).
2. A page whose `ValidationSummary` is present but rendered `style="display:none"`: `hides: ["#ValidationSummary1"]` must pass, and a shown one must fail (Task 3 live test `a_hidden_validation_summary_passes_hides`).
3. Page state echoed in an answer that is excerpted - a yellow screen, a one-off's answer body, a failing check's "the response began" - must still read `(page state)` (Task 4 test `no_page_state_reaches_a_report_record_or_log`; Task 3 live test `page_state_never_comes_back`).
4. A held browser still on the page from the previous run (the token page is not reloaded) holds that run's carried map: the next run must carry nothing (Task 3 live test `a_new_run_carries_nothing`; Task 4 test `each_run_has_its_own_carry_key`).
5. A checkbox the template unchecks with `""`, and a disabled control: the server must receive exactly what a browser would (Task 3 live test `a_postback_sends_what_the_browser_would_and_carries_the_answer`).
