# MCP & ADO REST Audit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce `claudedocs/mcp-audit-2026-08.md` — an evidence-backed findings report on our MCP protocol layer and ADO REST usage, audited against the MCP specification and `microsoft/azure-devops-mcp`, including a live interop smoke transcript. No production code changes.

**Architecture:** Five audit tasks feed one findings register. Tasks 2–4 each write candidate findings to their own file in the audit workspace; Task 5 adversarially verifies every candidate; Task 6 assembles the report. The reference repo and the Node smoke harness live in the session scratchpad, never in this repo.

**Tech Stack:** Reading Rust (`v2/src-tauri/src/mcp.rs`, `ai_bridge.rs`, `ado/*`); Node + `@modelcontextprotocol/sdk` for the smoke; the MCP spec at modelcontextprotocol.io and ADO REST docs at learn.microsoft.com as norms.

## Global Constraints

- **Zero production changes.** Nothing under `v2/` is edited. The only repo write is the final report in `claudedocs/` (+ this plan's checkboxes).
- **The real bridge handshake file is never written, renamed, or deleted** (`%TEMP%\tcm-v2-mcp-bridge.json` — a test once clobbered a live session). Bridge-down behavior is tested by giving the SPAWNED proxy a different `TEMP`/`TMP` env, never by touching the real file.
- **Read-only toward Azure DevOps.** The smoke calls only tools that answer without sign-in and without ADO traffic.
- Every finding carries dual evidence: our side (file:line) AND the norm side (spec section / reference file:line / ADO docs URL). Where our code and the reference disagree, **ADO documentation is the norm**; the reference is evidence of intent, not automatically correct.
- Audit workspace: `<scratchpad>/mcp-audit/` (scratchpad path is in the session's system prompt). Findings files: `findings-protocol.md`, `findings-smoke.md`, `findings-rest-<domain>.md`, all in that workspace.
- Findings severity vocabulary (exact strings): `broken`, `risky divergence`, `benign divergence`, `info`.
- Reference snapshot: the commit hash recorded in Task 1 is quoted by every reference citation.

- [ ] **Step 2: Audit each checklist row against `mcp.rs`**

The rows (from the design spec — audit ALL of these):
1. Newline-delimited JSON framing; no embedded newlines; UTF-8; garbage-line behavior.
2. `initialize`: response carries `protocolVersion` (what happens when the client offers a different version?), `capabilities`, `serverInfo`.
3. `notifications/initialized` accepted, never answered.
4. Requests arriving before `initialize`.
5. stdin EOF → clean shutdown.
6. `tools/list`: every entry has `name`, `description`, valid-JSON-Schema `inputSchema`; list is stable.
7. `tools/call`: results as `content` array; tool failures via `isError: true` content, not JSON-RPC errors.
8. Unknown tool name; schema-violating arguments.
9. JSON-RPC ids echoed for BOTH string and number ids.
10. Error codes: `-32700` / `-32600` / `-32601` / `-32602` used where the spec says.
11. Notifications (no id) never answered; unknown methods → `-32601`.
12. Bridge-down: proxy answers are well-formed MCP errors, not stdio garbage.
13. Capability honesty: we advertise only what we serve (no resources/prompts claims).

For each row: verdict (`sound` / one of the severity strings), our file:line, the spec section. **A spec row with no covering test in `tcm_mcp.rs` is itself a finding** (severity `info` if the code is sound, higher if unverifiable).

### Task 3: Protocol lane — live client-interop smoke

**Files:**
- Create: `<scratchpad>/mcp-audit/smoke/` (Node project), `<scratchpad>/mcp-audit/findings-smoke.md` (verdicts + full transcript)

**Interfaces:**
- Consumes: a debug `v2.exe` (`v2/src-tauri/target/gate/debug/v2.exe` — build with `CARGO_TARGET_DIR=target/gate cargo build` from `v2/src-tauri/` if absent). The running Test Case Manager app is NOT required for lifecycle/tools/list; the happy-path tool call needs the bridge up (the user's app running) — if it is not, record that sub-check as `not run` rather than failing the task.
- Produces: `findings-smoke.md`.

- [ ] **Step 1: Scaffold the harness**

```bash
mkdir -p "<scratchpad>/mcp-audit/smoke" && cd "<scratchpad>/mcp-audit/smoke"
npm init -y && npm install @modelcontextprotocol/sdk
```

Write `smoke.mjs`:

```js
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";

const EXE = process.argv[2]; // path to v2.exe
const env = { ...process.env };
if (process.argv[3] === "--no-bridge") {
  // Point the CHILD's temp dir away from the real handshake file.
  env.TEMP = env.TMP = process.cwd() + "\\empty-temp";
}
const transport = new StdioClientTransport({ command: EXE, args: ["--mcp"], env });
const client = new Client({ name: "conformance-smoke", version: "1.0.0" }, { capabilities: {} });
const log = (label, v) => console.log(`=== ${label} ===\n` + JSON.stringify(v, null, 1));

await client.connect(transport);                      // initialize + initialized
log("serverCapabilities", client.getServerCapabilities());
log("serverVersion", client.getServerVersion());
const tools = await client.listTools();
log("tools/list count", tools.tools.length);
log("tool names", tools.tools.map((t) => t.name));
if (process.argv[3] !== "--no-bridge") {
  // Cold-capable tool: no sign-in, no ADO traffic.
  const ok = await client.callTool({
    name: "validate_cases",
    arguments: { draft: JSON.stringify([{ title: "Smoke case", automation_status: "Planned", steps: [{ action: "a", expected: "b" }] }]) },
  });
  log("validate_cases", ok);
}
// Error paths - each must produce a WELL-FORMED error, not a hang/crash.
try { log("unknown tool", await client.callTool({ name: "no_such_tool", arguments: {} })); }
catch (e) { log("unknown tool -> error", String(e)); }
try { log("bad args", await client.callTool({ name: "validate_cases", arguments: { nonsense: 1 } })); }
catch (e) { log("bad args -> error", String(e)); }
await client.close();
console.log("SMOKE COMPLETE");
```

(Adapt the `validate_cases` argument key to the tool's actual inputSchema from tools/list — read it from the output rather than assuming; if `validate_cases` needs the bridge, use `check_spec_coverage` with inline `document` text instead. `mkdir empty-temp` before the no-bridge run.)

- [ ] **Step 2: Run both modes and capture**

```bash
node smoke.mjs "<repo>/v2/src-tauri/target/gate/debug/v2.exe" > transcript-live.txt 2>&1
mkdir -p empty-temp && node smoke.mjs "<repo>/v2/src-tauri/target/gate/debug/v2.exe" --no-bridge > transcript-nobridge.txt 2>&1
```

Expected: live transcript ends `SMOKE COMPLETE`, lists 15 tools; no-bridge run still completes lifecycle + tools/list and returns well-formed errors for tool calls (this validates checklist row 12 with a real client).

- [ ] **Step 3: Write `findings-smoke.md`** — verdict per sub-check, both transcripts inline, exact exe path + app-running state noted. A harness failure (npm/SDK) is reported as `not run` with the error — never skipped silently.

- [ ] **Step 1: Work items domain** — our `get_test_cases_by_ids` (GET `workitems?ids=` chunked 200) vs their batch approach; `search_pbis` (WIQL? their search domain); field-list construction; `update_work_item_fields` patch ops incl. the Tags `replace`-to-remove handling (verify OUR fix matches how the reference removes tags, and both against the ADO docs); create paths' `$Test%20Case` type encoding; project/org URL encoding with spaces.

- [ ] **Step 2: Test plans domain** — plans/suites list + requirement-suite create (api-versions, `vsrm` vs `dev.azure.com` hosts), test points list, run create/results/attachments (`resultScreenshots`), reset/finish flows vs their test-plans domain.

- [ ] **Step 3: Wiki domain** — our wiki search + page fetch vs their search/wiki domains (search API POST body shape, `includeContent`, path encoding).

- [ ] **Step 4: Cross-cutting** — api-version policy (our pinned `7.1` everywhere vs theirs); Authorization header construction; 429/Retry-After honoring; **paging**: for EVERY list endpoint in the inventory, does the response carry a continuation mechanism we ignore (`x-ms-continuationtoken` header, `$top` defaults)? Check the reference's paging handling for the same endpoints as the tiebreaker; the ADO docs page for each endpoint is the norm.

Each row: our file:line, reference file:line@REF_COMMIT, ADO docs URL when semantics are judged, verdict, note.
