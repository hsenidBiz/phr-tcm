# How To Use help site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Settings **How To Use** button opens a polished, offline documentation site (embedded in v2.exe) that explains every screen and button with interactive, automatically captured screenshots.

**Architecture:** `docs-site/` is a standalone Vite project (vanilla TypeScript + CSS, no React) whose content lives in typed per-screen files; it builds to one inlined `src-tauri/help/index.html` plus `img/`. Rust embeds that folder, writes it to the app's local data per version and opens it. A dev-only capture mode plus a Playwright-over-CDP script produce the screenshots and control positions from the content files themselves.

**Tech Stack:** Vite 7 (existing), vite-plugin-singlefile (new devDependency), TypeScript, CSS; Rust `include_dir` 0.7 (new dependency); playwright-core (existing).

**Spec:** `docs/superpowers/specs/2026-09-26-help-site-design.md`

## Global Constraints

- The site must work from `file://`, offline: one `index.html` with JS/CSS inlined, classic (non-module) script, no network URLs, fonts bundled from `@fontsource` files already in node_modules; images in `img/` beside it.
- It ships inside v2.exe (releases pack only the exe).
- Never show or name: Auto Run, autorun, hidden features (the list lives in docs-site/src/guard.test.ts), dev panel, demo data - in text, headings, alt text, file names, search index or screenshots.
- No real Azure DevOps data in screenshots: capture runs only on demo data.
- User-visible copy: plain task language, no em dashes.
- App-side: colours from theme tokens, icons from src/lib/actionIcons.ts named for what they do, Rust tests only in src-tauri/tests/suite/ (add a `mod` line in tests/suite/main.rs), bindings regenerated with `cd src-tauri && CARGO_TARGET_DIR=target/gate cargo test --test bindings`, user-facing errors name no URL.
- Commit via Bash heredoc with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. One build/test at a time. Vitest: `rtk proxy npx vitest run <files> --exclude "**/.claude/**"`. Never use `rtk proxy grep` with escaped double quotes in the pattern (it hangs) - use the Grep tool.

## Review Focus

1. Opening the site from a path with spaces (the app data path contains none, but the repo does) - open_path must receive a real path, not a URL-escaped one; pinned in Task 2.
2. A second click while the first write is running - must not interleave writes; pinned in Task 2 (write to a temp dir, rename into place).
3. A control whose accessible name contains a count (`Run 3 in runner`) - locate by regex, pinned in Task 1's types and Task 4's matcher.
4. Screen reader / keyboard use of the annotated shot - list rows focusable and announce the caption; pinned in Task 1.
5. A hidden-feature word leaking through a screenshot's visible UI (e.g. the sidebar in dev shows Auto Run) - capture mode must hide it before the shot; pinned in Task 3 and verified in Task 8 by inspecting shots.

**Interfaces (produces - later tasks rely on these exact names):**

```ts
// docs-site/src/types.ts
export type Locate =
  | { role: string; name: string }          // exact accessible name
  | { role: string; nameRe: string }        // RegExp source, e.g. "^Run \\d+ in runner$"
  | { label: string }                       // getByLabel
  | { text: string }                        // getByText exact
  | { testId: string };                     // data-testid / data-tour
export type Step =
  | { nav: string }                         // sidebar item's visible label, e.g. "Run Tests"
  | { click: Locate }
  | { press: string }                       // e.g. "Control+K", "Escape"
  | { waitFor: Locate }
  | { scrollTo: Locate }
  | { runnerWindow: true };                 // following steps and the shot target the runner window
export type Shot = { id: string; route: Step[]; alt: string };
export type Control = {
  id: string;                               // unique within the screen, kebab-case
  shot: string;                             // Shot.id it is marked on
  locate: Locate;
  name: string;                             // as the person sees it
  does: string;                             // what it does, plain words
  tips?: string[];
};
export type Screen = {
  id: string; title: string; group: Group; summary: string;
  shots: Shot[]; controls: Control[]; tips?: string[];
  howTo?: { title: string; steps: string[] }[];
};
export type Group = "Getting started" | "Test cases" | "Running tests" | "Work Manager" | "AI tools" | "Settings";
export type Positions = Record<string, Record<string, { x: number; y: number; w: number; h: number }>>;
export type Recipe = { id: string; title: string; steps: { text: string; link?: string }[] };
```

`src/content/index.ts` exports `screens: Screen[]` and `recipes: Recipe[]`. Images are `img/<theme>/<shot>.jpg` with theme `light` | `dark`, captured at 1440x900.

### Task 4: The capture script

**Files:** Create `scripts/docs-shots.mjs`; add `package.json` scripts `"docs:dev": "node scripts/docs-dev.mjs"` (sets `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` in the child env and spawns `npm run tauri dev`) with `scripts/docs-dev.mjs`, and `"docs:shots": "node scripts/docs-shots.mjs"`. Content is TypeScript: load it with `npx tsx`-free approach - build the registry to JSON first: add `docs-site/src/content/export.ts` run by vite-node? Simplest: the script runs `npx vite-node docs-site/src/content/dump.ts` (vite-node ships with vitest) which prints the registry as JSON to stdout.

**Behaviour:**
1. `--validate` (no app needed): load the registry, check every control's `shot` exists, every shot has a route, ids unique; exit 1 listing problems. Used by tests.
2. Connect `chromium.connectOverCDP("http://127.0.0.1:9333")`; if it fails print: "Start the app with `npm run docs:dev`, wait for it to open, then run this again." and exit 1.
3. Main page = the target whose URL has no `#runner`. Set localStorage `tcm-v2-dev-demo`="on" (and whatever demo mode needs - read src/dev/demo.ts `toggleDemoMode`), `tcm-v2-dev-capture`="on", the theme key for the pass (read src/lib/theme.ts: `light` / `slate`), reload, `page.setViewportSize({ width: 1440, height: 900 })`, wait for the first screen.
4. For each theme pass and each shot: reset to a known start (reload), run its `route` steps (`nav` = click the sidebar item by its label; `runnerWindow` = wait for the new target with `#runner` and switch to it), wait for network idle + 400 ms for animations, `page.screenshot({ path: docs-site/shots/<light|dark>/<shot>.jpg, type: "jpeg", quality: 88 })`; then for each control on that shot resolve its `locate` (role+name via `getByRole(role, { name, exact: true })`, `nameRe` via `new RegExp`, label/text/testId via the matching getBy) and record `boundingBox()` rounded, into positions (record from the light pass only - layout is identical across themes; assert the dark pass finds them too).
5. Any control not found or not visible: collect and print `shot / control id / locate`, exit 1 (do not write positions for that run).
6. Write `docs-site/shots/positions.json` (stable key order).
