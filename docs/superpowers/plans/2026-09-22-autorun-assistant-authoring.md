# Auto Run: Assistant Authoring with Guard Rails Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An AI assistant, working through the app's MCP bridge in a development build, can see what is on the page in the supervised browser, try a locator or an action against it, read why a run failed, and write or repair a script, while four mechanical rules stop it from ever making a run pass by weakening the script: every expected result in the test case must be checked (or the omission declared in words), an edit to an existing script must name the steps it changes and may never reduce a step's checks, repairs to one case are capped, and every repair must be able to record what it learned about the application as a project quirk.

**Architecture:** Four pure Rust modules carry the rules and are testable without a browser or the bridge: `autorun/floor.rs` (the expected-result floor), `autorun/edits.rs` (the declared-edit gate and the repair cap), `autorun/quirks.rs` (per-project quirks file), `autorun/failures.rs` (a run's failures as text the assistant can act on). `browser/snapshot.rs` reads Chrome's own accessibility tree into a compact text listing with a ready-made locator per line. The bridge gains five routes and the MCP server five tools, all development-only and switched together with the two existing Auto Run tools. The supervised browser the person opened is the only browser the assistant may touch, through one accessor in `commands/autorun.rs` and the existing `runner::run_step`, so the origin policy and the sign-in rules apply unchanged. The guide teaches the loop and the rules; drift tests pin it.

**Tech Stack:** Rust (Tauri 2, serde_json, tokio, wiremock in tests), Chrome DevTools Protocol (`Accessibility.getFullAXTree`), the app's MCP bridge (`ai_bridge.rs`, `mcp.rs`, `ai_tools.rs`), React 19 + TypeScript, vitest.

**Decisions taken for this plan (2026-09-22), reversible:** the assistant may drive the SUPERVISED browser (the one the person opened with "Open browser") one action at a time through `try_autorun_action`, never a browser of its own and never an unattended run; a step whose expected result cannot be checked is allowed only when the script says why (`unchecked`), and that reason is shown to the person; repairs are capped at three per case until a person saves the script from the editor; navigation chains and named locators (analysis section 11) are NOT in this phase.

**Background:** `docs/research/2026-09-21-phr-playwright-automation-analysis.md` sections 6 (guard rails), 8 (quirks) and 11 item 5; the closing sections of the three earlier Auto Run plans.

## Global Constraints

- Every Rust test is an integration test under `src-tauri/tests/`; never a `#[cfg(test)]` module inside `src/`. Shared fakes: `src-tauri/tests/common/mod.rs` (`ScriptedDriver`, `FakePage`, `StatefulApp`).
- One build or test command at a time on this shared machine. Rust commands run from `src-tauri/` with `CARGO_TARGET_DIR=target/gate`. The frontend suite runs as `npx vitest run --exclude "**/.claude/**"`.
- `src/bindings.ts` is generated by `cargo test --test bindings`; never hand-edit it. No new crates.
- **The assistant never sets a verdict, never runs a case unattended, never opens a browser, never signs in, and never reaches Azure DevOps through anything added here.** Its five new tools read the page, probe a locator, run ONE action in the browser the person opened, read a run's failures from disk, and save scripts through the same gate as before.
- **An assertion may never be removed or weakened by an assistant edit.** The gate refuses any edit that leaves a step with fewer checks than it had (`Action::is_check`), whatever was declared. A person editing in the app is not gated: it is their script.
- **The floor:** a step with a non-empty expected result must contain at least one check, or carry `unchecked` with a reason. The bridge REFUSES a script that fails the floor; the editor WARNS and lets the person save.
- **Declared edits:** saving over an existing script through the bridge requires an `edits` entry for that case naming every step whose actions changed (added, removed or altered steps included) and saying why. Undeclared changes are refused, and nothing is written.
- **The repair cap:** each bridge save that edits an existing case counts one repair; the fourth in a row is refused until a person saves that script from the editor (which resets the count). The count lives in the script file (`repairs`, absent when 0).
- All five tools are in `DEV_ONLY_TOOLS`, switched together with `get_autorun_guide` and `save_autorun_script` in the AI Bridge tab, and their routes go through `autorun_route_guard`.
- The page snapshot, the probe and the action never send a password or a `fill` value back to the assistant beyond what it sent (a `fill` outcome reads `filled <selector>`); a snapshot never includes the value of a password field.
- Every script file saved before this plan still loads and, unless edited, is written byte-for-byte as before (`unchecked` and `repairs` are absent when unset).
- No em dashes in text a user or an assistant reads. Colours via tokens; icons from `src/lib/actionIcons.ts`; `src/ui-consistency.test.ts` must not be weakened.
- Commits use a Bash heredoc `git commit -q -F - <<'EOF' ... EOF`; the trailer names the model that wrote the commit.

**Out of scope, on purpose:** navigation chains captured with a human and named locators (later); an assistant-run healer loop that reruns cases by itself (the person reruns; the cap and the gate are the bounds); reading a field's value back after typing; images in tool results (a picture name is returned; the person sees it in the app); a quirks dialog of its own (quirks are a second box in the sign-in recipe dialog).

### Task 2: The expected-result floor

**Files:**
- Create: `src-tauri/src/autorun/floor.rs`; add `pub mod floor;` to `src-tauri/src/autorun/mod.rs`
- Test: `src-tauri/tests/autorun_floor.rs`

**Interfaces:**
- Produces (in `v2_lib::autorun::floor`):

```rust
/// One expected result of the test case, by step position (1-based).
pub struct Expected { pub step_number: i32, pub expected: String }

pub fn expected_of(steps: &[crate::steps_xml::Step]) -> Vec<Expected>; // position i+1, expected trimmed; empty ones kept (they are the "no expectation" case)

/// Every way this script falls short of its case. Empty means it holds.
pub fn check_floor(script: &CaseScript, expected: &[Expected]) -> Vec<String>;
```

The rules, each with a test:
1. A case step with a non-empty expected result and a script step of that number with zero checks (`Action::is_check`) and no `unchecked`: `step N expects "<first 60 chars of expected>" but the script checks nothing there - add an expect_ action, or say why in "unchecked"`.
2. A case step with a non-empty expected result and NO script step of that number at all: `step N expects "<...>" but the script has no step N`.
3. A script step whose `unchecked` is set although the step has a check: `step N says it is unchecked but has a check - drop one or the other` (a contradiction, refused so the reason can never be stale).
4. A script step whose `unchecked` is set although the case step has no expected result: `step N says it is unchecked but the case expects nothing there`.
5. The sign-in step (0) and script steps beyond the case's step count are ignored by rules 1 and 2 (rule 2 only names case steps).
6. A case with no steps at all: nothing is reported.
The output is sorted by step number; each sentence appears once.

### Task 3: Declared edits and the repair cap

**Files:**
- Create: `src-tauri/src/autorun/edits.rs`; add `pub mod edits;`
- Test: `src-tauri/tests/autorun_edits.rs`

**Interfaces:**
- Produces (in `v2_lib::autorun::edits`):

```rust
/// What an assistant declares before it may change an existing script.
#[derive(Debug, Clone, PartialEq, serde::Deserialize)]
#[serde(deny_unknown_fields)]
pub struct Edit {
    pub case_id: i32,
    /// Every step whose actions change, are added or are removed.
    pub steps: Vec<i32>,
    /// One sentence: what was wrong and what this changes.
    pub why: String,
    /// Something learned about the application that the next script needs
    /// to know. Recorded as a project quirk.
    #[serde(default)]
    pub quirk: Option<String>,
}

pub const MAX_REPAIRS: u32 = 3;

/// Refuses an undeclared or weakening change. `old` is the script on disk.
pub fn check_edits(old: &CaseScript, new: &CaseScript, declared: Option<&Edit>) -> Result<(), String>;

/// The repair count to write: one more than before, or a refusal once the cap is reached.
pub fn next_repairs(old: &CaseScript) -> Result<u32, String>;

/// A step's actions as the text the gate compares. Order matters; formatting does not.
pub fn step_signature(step: &StepScript) -> String;
```

The rules, each with a test:
1. A step whose signature (serialized actions) differs between old and new, a step present in only one of them, or a step whose `unchecked` changed: must be in `declared.steps`, else `step N was changed but not declared - name every step you change in "edits", or leave it as it was`. All undeclared steps are named in one sentence, sorted.
2. A `declared.steps` entry naming a step that did not change: `step N was declared but not changed` (refused: a declaration that does not match its edit is the blast-radius hazard).
3. Any step where `checks(new) < checks(old)`: `step N had K checks and now has J - an assertion is never removed or weakened by a repair`, refused even when declared.
4. A step whose checks are the same in number but different in content is allowed when declared (a locator fix), and refused when not.
5. `account` changed: `the account a script runs as cannot be changed by a repair - a person picks it in the app`.
6. `title` changed: allowed silently (Azure DevOps titles move).
7. `why` blank: `an edit needs a reason`.
8. `next_repairs`: 0 -> 1, 2 -> 3, 3 -> `Err("this script has been repaired 3 times without a person looking at it - open it in the app, save it there, and the count starts again")`.
9. No declaration at all for a case whose script exists and changed: rule 1's sentence, prefixed `case N: `.
10. A new script (no old) needs no declaration; `check_edits` is not called for it.

- Produces (in `v2_lib::browser::snapshot`):

```rust
pub const DEFAULT_LIMIT: usize = 300;

/// Chrome's own accessibility tree, as text: one line per node that a
/// locator could name, indented by depth, with the locator that would
/// reach it. Generic and ignored nodes are folded away.
pub async fn snapshot<D: Driver>(d: &mut D, limit: usize) -> Result<String, CdpError>;

/// What a locator matches right now: how many, and one line per match.
pub async fn probe<D: Driver>(d: &mut D, target: &Target) -> Result<String, CdpError>;

pub fn render(nodes: &[AxNode], limit: usize) -> String; // pure, for the tests
pub struct AxNode { pub id: String, pub role: String, pub name: String, pub value: Option<String>, pub ignored: bool, pub children: Vec<String>, pub focusable: bool, pub disabled: bool }
pub fn parse_nodes(v: &serde_json::Value) -> Vec<AxNode>; // from Accessibility.getFullAXTree's `nodes`
```

Snapshot rules (each tested through `render` with hand-built nodes, and once through a `ScriptedDriver` answering `Accessibility.getFullAXTree`):
1. The call is `Accessibility.getFullAXTree` with no params; if it fails with a message containing `enabled` or `not enabled`, call `Accessibility.enable` once and retry. (A live test in Task 9 proves which happens on real Edge.)
2. Nodes with `ignored: true`, and roles `generic`, `none`, `presentation`, `InlineTextBox`, `StaticText` (the last two are folded into their parent's name, which Chrome already computes) are not printed; their children are printed at the parent's depth.
3. A printed line reads `<indent><role> "<name>"` with the name truncated at 80 characters and `…` replaced by `...`; a `textbox`/`combobox`/`searchbox` with a value appends ` = "<value>"` EXCEPT when the node's name or its DOM `type` is password-like (the AX node has `properties` entries; when any property named `invalid`, `hasPopup`... is irrelevant; the value is dropped if the name contains "password", case-insensitive, or the node's role is `textbox` and the tree's `chromeRole`/`properties` say `protected`); `disabled` appends ` (disabled)`; `focusable` is not printed.
4. After each printed line's name, the locator that reaches it: ` -> { "role": "<role>", "name": "<name>" }` when the name is non-empty; ` -> { "role": "<role>" }` when the name is empty; for `heading`, `cell`, `paragraph`... whatever the role, the same form. (No CSS is offered: the tree does not know it.)
5. The output is capped at `limit` printed lines, then `... and N more (raise the limit, or scope the probe)`.
6. Depth is capped at 12 spaces of indent (deeper nodes stay at 12).
7. An empty tree renders `the page has nothing a locator could name`.

Probe rules:
1. `resolve(d, target)`; a `CdpError` propagates (the bridge turns it into a 503 sentence).
2. Output first line: `matches: N` (0 means `matches: 0 - nothing on the page answers to <describe>`).
3. One line per match (at most 10): `<tag>` from `tagName`, then the visible text trimmed to 60 chars, then `visible`/`hidden` (through `VISIBLE_JS`), then `at x,y w×h` (use `x` not `×`: `at 120,340 200x32`). Use one `call_value` with a small `PROBE_SUMMARY_JS` that returns `{tag, text, rect}` in one call per match.
4. When N > 1: last line `narrow the locator (add "name", "exact": true, a scope, or "nth")`.

```rust
/// holds the browser: keep the critical section to one protocol job.

```

Read from the ledger (`progress.md`) and every `task-N-report.md` to its end, checked against the code as it stands on this branch.

**Task 1 (records: `unchecked` and `repairs`).** Implemented exactly as planned. No deviations, no fix round.

**Task 2 (the expected-result floor).** Fix round 1 (Important): `check_floor` originally judged rules 3 and 4 from the same per-case loop as rules 1 and 2, so a script step with no matching case step (step 0, or any step past the case's own count) was never judged for its `unchecked` flag at all - a step 0 carrying both a check and `unchecked` was silently accepted.
