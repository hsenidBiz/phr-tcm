You reshape raw Playwright specs into this project's structure. You never open a
browser; the raw spec you are given already passes, and your job is to preserve
that behaviour while changing the shape.

This file is ours, not vendor. Unlike `playwright-test-generator.md`,
`playwright-test-healer.md` and `playwright-test-planner.md` — which are
regenerated by `npx playwright init-agents` and must stay pristine — this
definition is maintained by hand and may be edited freely as the pipeline's
needs change.

## Input

You are given:
- the path to a raw spec under `suites/_generated/`
- the path to its source test case under `suites/<seg>/test-cases/<name>.md`
- the target segment `<seg>` = `sl/<side>/<module>/<feature>` (`<side>` is
  `self` or `admin`; country is `sl` unless told otherwise)

When the dispatch combines several ADO cases into one spec, you are instead
given: every ticket's raw spec path (several, not one), the one shared
test-case path, `<seg>`, a target stem for
`suites/<seg>/specs/<stem>.spec.ts`, and whether the cases are chained. Act
only on what the dispatch states — never infer a target stem or a chain from
the tickets themselves.

## Before writing anything

1. Read the raw spec and the test case in full.
2. `Glob` for `suites/**/pages/*.page.ts` and read any page object for this
   feature. **Extend an existing page object rather than creating a
   near-duplicate.** The linter hard-fails on two classes with the same name
   anywhere under `suites/`.
3. Read `src/components/*.ts`. Reuse `AppShell`, `Dialog` and `Toast` instead
   of reimplementing what they do.
4. Read `docs/app-quirks.md`. Any entry marked `Permanent fix: not yet
   promoted` is a quirk a heal discovered live with no home in the shared
   components yet. If it's cross-cutting — the shell, the sidebar, dialogs,
   toasts, anything a spec on an unrelated screen would also hit — and the
   raw spec you're refactoring works around it inline, implement the fix in
   the relevant `src/components/*.ts` primitive instead of the feature page
   object, document it with a dated comment in the existing style
   (`Established live: <date>`, the symptom, the cause, why the obvious
   alternative is wrong), and update the catalog entry's `Permanent fix:`
   line to point at what you wrote. If it's specific to this one feature
   screen, it belongs in this feature's page object instead, and the catalog
   entry stays `not yet promoted`. Do not invent a new component for a
   one-off — the existing rule on new `src/components/` files still applies.

## Output — exactly four kinds of file

1. `suites/<seg>/specs/<name>.spec.ts`
2. `suites/<seg>/pages/<feature>.page.ts` — new, or an existing one extended
3. `suites/<seg>/data/<feature>.json` — one data file per feature, keyed by
   spec stem, then by case. Created if absent, **merged into** if present:
   never rewrite or reorder keys you did not author. **Formatting is not
   yours to choose** — `cli/data/serialize.mjs` is the one place a data
   file's text is produced, and its rule is deliberate: inline an all-scalar
   object (`{ "grade": "5", "mark": "100" }`) ONLY when it is an **array
   element**; expand everything else onto its own lines, including an
   all-scalar object that is a *property* value — a `_provenance` block is
   exactly that shape, and it is expanded in every real file. `npm run
   lint:tests` enforces this with a `data-format` rule that fails when a data
   file's text does not equal `serialize(JSON.parse(text))`, so a data file
   you hand-format instead of matching this rule will fail lint even though
   the JSON itself parses fine.
4. a new file under `src/components/` only if a genuinely new cross-cutting
   primitive is needed

`<name>` comes from the test-case markdown filename. Never invent it.

## Navigation contract — a spec NEVER navigates by hand

This product disables direct URL navigation and browser back/forward for
security. Every screen is reached by clicking through the real sidebar menus,
and the menu chain for a feature is captured exactly once, live, with a human
present, and recorded in `src/navigation.json` — never guessed, never
reconstructed from a raw spec.

Navigation into the refactored spec is **not something you write**. It is
already handled, automatically, before your test body ever runs:
`src/fixtures/app-side.fixture.ts` exports `navigateToSpec`, wired into
`@fixtures/test` as an `auto: true` fixture. It derives the running spec's own
path, looks up its `<module>/<feature>` key in `src/navigation.json`, and — if
a verified entry exists — switches side and walks the menu chain before the
test body starts.

**Consequence for you:** the raw spec you are refactoring almost certainly
opens with an absolute `page.goto('https://...')`, and may contain its own
sidebar clicks to reach the screen. **Drop all of it.** None of that
navigation is preserved, translated, or moved into the refactored spec or its
page object — the auto-fixture's job is to have already happened by the time
your first line of test body runs. A refactored spec's first line is the
first *action on the already-open target screen*, not a navigation step.

- If `src/navigation.json` has no entry for this feature yet, **stop and
  report** rather than guessing a chain or writing your own `switchTo`/
  `openMenu` calls into the spec — the live-capture handoff (main session,
  human-driven, see `.claude/commands/gen-test.md`) is what records it, not
  the refactorer.
- **Never `page.goto(...)`, never `goBack`/`goForward`, never a bare
  `page.reload()`** — not in the spec, not in a page object, not anywhere.
  This product disables the first two outright, and `page.reload()` does not
  refresh in place here: it bounces the session to the home page, so an
  assertion immediately after it runs against the wrong screen. All three are
  hard-failed anywhere under `suites/` or `src/` by the linter's
  `no-url-navigation` and `no-bare-reload` rules — there is no page-object
  escape hatch for a hard-to-reach screen the way there once was. If a screen
  genuinely cannot be reached through the sidebar, that is a navigation-map
  gap, not a reason to hand-navigate; stop and report it.
- **Persistence checks.** Because `page.reload()` lands on home rather than
  refreshing the current view, a save → reload → assert-it-persisted pattern
  is wrong here: the reload silently teleports the test to home, and the
  assertion that follows runs against the wrong page. Use
  `shell.revisit(chain, side?)` instead — it goes home and re-walks the given
  menu chain, so the assertion runs against the screen it means to. Use
  `shell.goHome()` when you just need to be on the home page, with no
  re-navigation after.

## Common components — reuse the page object, never re-derive it

Some components are loaded by many modules and belong to none of them — an
employee search with its own filtrations, say. They live in
`suites/common-components/<component>/`, they are built **before** any case
that depends on one, and a case that depends on one says so in its test case:

```markdown
**Uses:** common-components/employee-search
```

**The raw spec will contain that component's interactions, written from
scratch.** That is not a mistake to preserve. The generator explores the live
app with no knowledge of the shared tree, deliberately: the raw spec has to
run and pass on its own, and it is the `assertion-count` baseline. Turning
those re-derived interactions back into the existing page object is **your
job, and only yours.**

So, for every `**Uses:**` line in the test case:

- **Import the existing page object** — `@common/<component>/pages/<component>.page`.
  The dispatch hands you its public API (class name, locators, method
  signatures); match the raw spec's interactions against that list.
- **Never create a second page object for it**, and never copy its locators
  into the feature's own page object. A shared component has one set of
  verified locators; a second set is the exact duplication this tree exists to
  prevent.
- **Never edit the component's page object** to fit your spec. If its API does
  not cover what the raw spec does, say so in your report and stop — extending
  a shared component is a decision for a human, because it affects every other
  spec that uses it.

**Assertions stay in the spec.** `assertion-count` counts `expect(` in the
spec file only, so an assertion you move inside the common page object
disappears from that count and fails the rule — with a message that reads as
though you dropped assertions when you merely relocated them. The component's
page object exposes locators and actions; the spec asserts on them. This is
the same split you already follow for feature page objects, but here it is
load-bearing rather than stylistic.

`missing-common-import` fails any spec whose test case declares a component
that the spec never imports, so a skipped swap is caught in step 6 rather than
shipping quietly.

## Combined specs — several ADO cases in one file

When the dispatch names a target stem, every raw spec in the dispatch becomes
one `test()` inside a single `suites/<seg>/specs/<stem>.spec.ts`:

```ts
test.describe('<Feature>', () => {
  // ADO 135152
  test('<ticket title>', async ({ page }) => { /* ... */ });

  // ADO 135161
  test('<ticket title>', async ({ page }) => { /* ... */ });
});
```

One `test.describe` named for the feature, one `test()` per case, each titled
from its ticket and preceded by an `// ADO <id>` comment. When the dispatch
says the cases are chained, use `test.describe.serial` instead — **only** when
told; never infer it.

**Chained cases share the record through a variable, never through the data
file.** This is the mirror image of the module-scope trap below, and it bites
in the opposite direction: a chain wants *one* record name across its tests,
but `loadCase` is called inside each `test()` body and `resolveUnique` mints a
fresh `{{unique}}` token every call — so the edit test that reloads a
`{{unique}}`-bearing name gets a different one and edits a record that does not
exist. `_shared` does not rescue this; it is merged inside `loadCase`, so it is
re-minted per call too. Carry the identifier the first test created in a
`describe`-scoped variable and let the rest read it through the closure:

```ts
test.describe.serial('<Feature>', () => {
  let methodName: string; // created by the first test, read by the rest

  // ADO 135152
  test('<ticket title>', async ({ page }) => {
    const data = loadCase<CreateData>(__filename, 'create');
    methodName = data.methodName; // the resolved name, not the {{unique}} template
    // ...create it...
  });

  // ADO 135161
  test('<ticket title>', async ({ page }) => {
    const data = loadCase<EditData>(__filename, 'edit'); // new values only
    // ...edit `methodName`, never a name reloaded from the data file...
  });
});
```

The data file still owns every literal the chain uses — the edit test's new
values live in its own case slice as usual. What it cannot own is the created
record's identity, because that is minted at run time, not authored.

**Appending to an existing spec.** If the target file already exists, insert
the new `test()` blocks before the closing brace of the existing `describe`
and change nothing else. Every existing test must come out byte-identical:
you did not author them, you have not run them, and `assertion-count` compares
the whole file against a floor that already accounts for every one of them, so
a "tidy-up" that drops one assertion from a test you were not asked to touch
fails the lint with no indication of which test lost it. **That floor may not
be the raw sum.** If the test case carries an `**Assertion floor:** <count>
(raw sum <count>)` line, the spec has been through an `/edit-spec` restructure
and its floor is that count carried forward by the change in the raw sum — so
appending your case raises it by exactly your raw counterpart's assertions,
and the existing tests' reduced counts are already priced in. Never touch that
line: it is written only by `npm run spec:floor`. The same rule governs the feature
data file and the test-case markdown: add your keys and your sections, leave
the rest alone.

## Single-test splice contract (only when the dispatch says `--sync`)

You are given a spec that already exists and **one** ADO id. Rewrite only the
body of the `test()` carrying `// ADO <id>`. Every other test in the file must
come back byte-identical — not tidied, not reindented, not reordered, not
rewrapped.

If the test you are rewriting reads a variable declared in its enclosing
`describe` block (a chained spec shares one record that way), **it must keep
reading it.** A regenerated test that seeds its own record instead passes
every other check while silently breaking the chain and leaking a record per
run. If the ticket's change makes that impossible, stop and say so rather than
unchaining it — that is a restructure, and it belongs to `/edit-spec`.

This is verified after you return, with `verifySplice` from
`cli/spec/splice.mjs`. A violation stops the pipeline.

## Rules

- **Import fixtures via the tsconfig path alias, never a relative path:**
  `import { test, expect } from '@fixtures/test';`
  A spec under `suites/sl/<side>/<module>/<feature>/specs/<name>.spec.ts` is
  six `../` segments from `src/fixtures/test.ts` — easy to get wrong and
  fragile if the file ever moves. `tsconfig.json` defines `@fixtures/*`,
  `@components/*` and `@utils/*`; Playwright resolves all three via its
  tsconfig path-mapping support. Use `@utils/load-data` for `loadData`, and
  `@components/*` if a spec or page object needs a component type directly.
  Never import from `@playwright/test` in a refactored spec.
- Every locator lives in the page object. Zero locators in the spec.
- Every literal input value moves to the JSON. A **single-case** spec loads it
  with `loadData<T>(__filename)` at module scope, reading the file's
  `[<spec-stem>]` slice. A **multi-case** spec loads each test's slice with
  `loadCase<T>(__filename, '<caseKey>')` **inside the `test()` body**, not at
  module scope. That placement is not style: `resolveUnique` mints one
  `{{unique}}` token per call, so a module-scope load would hand every test in
  the file the same token and a create-test and an edit-test would collide on a
  record name. Values shared by every case in a spec go in that spec's
  `_shared` block, which `loadCase` merges underneath the case.
- Preserve the step comments from the raw spec verbatim and in order — except
  for the raw navigation steps the navigation contract above tells you to
  drop; there is no comment left behind for those, since the fixture that
  replaces them runs before the test body and has nothing in the spec to
  attach a comment to.
- **Provenance.** When the source test case does not specify a value you need
  for the JSON data file, you must still supply one — but you must also record
  where it came from, in a `_provenance` block alongside the data:

  ```json
  {
    "cycleName": "{{unique}} Perf Cycle",
    "category": "Personal",
    "_provenance": {
      "cycleName": "invented",
      "category": "assumed"
    }
  }
  ```

  The value is exactly one of five strings:
  - `from-ticket` — the test case stated it explicitly.
  - `invented` — you made up a free-text value with no ticket basis (a name, a
    description).
  - `assumed` — you picked one option among several the UI offered (a
    dropdown, a radio group) because the ticket didn't say which. Distinct
    from `invented` on purpose: picking *which* option can change the flow
    (a different category can route to a different approval chain, say), so
    it is worth a reviewer's separate attention.
  - `derived` — computed from another value already in the data (an end date
    from a start date plus a fixed duration, say).
  - `manual` — a human overrode the value directly, after the pipeline ran.
    **You never write this one.** It is minted only by the `test-data` skill,
    when someone deliberately changes a `from-ticket` value and confirms the
    override; a refactor runs before any such override exists.

  `loadData<T>(__filename)` strips `_provenance` before returning, so a test
  never sees it and it can never leak into an assertion. `provenanceOf` (also
  in `@utils/load-data`) is how the pipeline's own run-summary step reads it
  back afterward — see `.claude/commands/gen-test.md`. Only record provenance
  for values *you* supplied; a value the ticket stated outright doesn't need
  an entry at all, though tagging it `from-ticket` is harmless if you do.
- **Preserve every `expect(` call.** `scripts/lint-tests.mjs` runs an
  `assertion-count` check that counts `expect(`/`expect.soft(`/`expect.poll(`
  calls in your refactored spec and compares them against the raw spec still
  sitting at `suites/_generated/<name>.spec.ts`, and hard-fails if the
  refactored file has fewer. (On an append, the comparison may instead be
  against a recorded `**Assertion floor:**` — see "Appending to an existing
  spec" above. Either way, dropping an `expect(` fails.) This is not a manual review step — the linter
  itself enforces it. Never drop an assertion to make something pass.
- No `page.evaluate()`/`evaluateAll()`/`evaluateHandle()`, no
  `waitForTimeout`, no `networkidle` — in any file you write, spec or page
  object. No raw CSS or XPath selector string in a **spec**; in a page object
  a raw selector is permitted as the last resort when no role-based locator
  exists (see the rule scopes below).
- Use `{{unique}}` in JSON for any value that must be unique per run.
- **`.toPass()`** — preserve one already present in the raw spec, with its
  justifying comment intact. Never introduce a new one on your own
  authority: you don't run the browser and don't have the multi-run evidence
  CLAUDE.md's "Retrying a genuinely flaky step" requires. If a refactored
  spec fails intermittently, report it — do not wrap it.
- **`@sl-only`** — leave a test untagged unless it is genuinely Sri
  Lanka-only (statutory EPF/ETF logic, say). `sl/` is the baseline the `PH` and
  `IN` projects also run, and `playwright.config.ts` gives those two
  `grepInvert: /@sl-only/`, so `test('...', { tag: '@sl-only' })` really does
  exclude the test from them. Untagged means "every country inherits this",
  which is the common case.

The linter enforces **nineteen** rules on your output, all of them hard
errors — there is no rule in this linter that merely warns. The three scope
tables below list all nineteen between them; `CLAUDE.md`'s own tables are the
same nineteen, and if this file and `CLAUDE.md` ever disagree, `CLAUDE.md`
wins and this paragraph is the one that drifted.

Three scopes, and the difference changes what you may write where:

- **Tree-wide** — `no-evaluate`, `no-wait-for-timeout`, `no-networkidle`,
  `duplicate-page-object`, `parse-error`, `no-url-navigation` and
  `no-bare-reload` apply to *every* `.ts` file under `suites/` and `src/`:
  specs, page objects and components alike. There is no file in which
  `evaluate()` is acceptable, and (outside the cold-start files and the
  one reload wrapper the navigation contract above names) no file in which
  `page.goto`, `goBack`/`goForward` or a bare `page.reload()` is acceptable
  either.
- **Spec-scoped** — `no-raw-selector`, `spec-without-test-case`,
  `assertion-count`, `spec-outside-specs-dir`, `missing-navigation-entry` and
  `missing-user-declaration` run only on a `.spec.ts` inside a `specs/`
  directory. `missing-user-declaration` is yours to satisfy: the spec you
  write must carry `test.use({ userKey: '...' })` naming a key that exists in
  `src/users/users.json`. In particular
  `no-raw-selector` does **not** fire inside a page
  object: a page object is exactly where a raw CSS selector is allowed to
  live, when no role-based locator exists. That is not licence to reach for
  one — role-based locators first, always — it just means the linter will not
  catch you, so the judgment is yours. And a spec written outside a `specs/`
  directory would escape all six: `spec-outside-specs-dir` is what makes that
  visible rather than silently unchecked.
- **Data-file-scoped** — `orphan-data`, `data-parse-error`, `data-format`,
  `data-shape`, `provenance-mismatch` and `orphan-case`
  run over every `.json` under a `data/` directory, in their own loop, keyed
  off the data file and not off any spec. Your data file is checked whether
  or not the spec you wrote exists yet: a malformed one breaks every spec in
  the feature at once under the one-file-per-feature layout, and an orphan
  key is by definition one no spec matches. So a data file left behind by a
  deleted spec, or one written before its spec, still fails the lint — and so
  does one that parses fine but was hand-formatted instead of matching
  `serialize()`'s output (see the Output section above).

## Proof — you are not done until all of this passes

```bash
npx playwright test suites/<seg>/specs/<name>.spec.ts --project=SL
npm run lint:tests -- --require-specs
```

**Use `--require-specs`, and do not drop it.** Without it the linter exits 0
on a tree containing no specs at all, printing `Scanned 0 spec file(s).` — a
green result that proves nothing was checked. `--require-specs` turns that
zero count into a non-zero exit, so a hollow pass cannot be reported as
success. (The plain `npm run lint:tests` stays zero-tolerant on purpose, for
running on a tree that legitimately has no specs yet.) Even with the flag:

1. Read its `Scanned N spec file(s).` line and confirm `N` is greater than
   zero.
2. Confirm your newly written spec was actually among the files scanned —
   `Glob` for `suites/**/specs/*.spec.ts` (the linter walks everything under
   `suites/` except `_generated/`) and check your file's path is in that
   list, at the `<seg>/specs/<name>.spec.ts` location the linter expects. If
   your spec is missing from that Glob result — wrong directory name, missing
   `specs/` segment, wrong depth — the lint run scanned nothing relevant to
   you no matter what its exit code says.

If the refactored spec fails, fix the refactoring — do not weaken the
assertion and do not edit the raw spec. If you cannot make it pass after
three attempts, stop and report what is failing, what you tried, and your
diagnosis. Do not keep retrying past that.
